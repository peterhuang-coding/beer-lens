# 购买决策：在这个价格下，哪杯更适合我？

状态：首期菜单内决策已实现，2026-09-14。预算、ABV、IBU、单位价、总价差与连续追问具备确定性路径；市场报价和购买反馈闭环仍待实现。

## 要替用户做的决定

用户需要一个具体选择，并理解取舍：今天买哪款、实际花多少钱、为什么选它、多花钱是否值得，以及什么情况下先不买。

回答围绕五项信息组织：**首选、实际杯价与容量、选择理由、备选差价、缺失证据**。识别结果是建立候选的输入，最终交付是购买建议。

## 如何定义“值”

| 判断 | 依据 | 能给出的结论 |
| :--- | :--- | :--- |
| 买得起、喝得合适 | 单杯／总预算、期望容量、风格、苦味、酒精度、个人偏好 | 先排除不符合本次要求的候选 |
| 花费更合理 | 当前菜单的价格、容量、币种、包装与消费形式 | 计算单位价，说明同样容量或多花几元的差别 |
| 品质与体验有依据 | 已确认酒款的评分与样本量、风格、个人品饮记录、新鲜度证据 | 解释为什么可能适合，并保留不确定项 |

单位价用 `价格 ÷ 容量 × 100` 计算为每 100ml 价格，作为花费参照。容量更大不必然更适合：用户只想喝一小杯时，不能为了单位价低而推荐大杯或整组装。

比较必须有明确范围。当前酒单可称“这几款中单位价最低”；只有获得同款、同规格、同币种、同消费形式且带时间和来源的报价，才可以讨论相对市场价格。堂饮服务、外带、罐装和不同批次不能直接混在一起比较。没有外部报价时，不声称“全网最低”或“低于市场”。

不将评分直接除以价格作为通用性价比分。评分不是线性效用，个人口味、数据可信度和场景也不能由一个未经验证的综合分替代。

## 主示例与真实基础

## 最小实现顺序

1. **继续补 Offer 语义。** 增加币种、杯型、包装与套餐；未知字段不补造。
2. **验证真实用户取舍。** 用真实点单任务比较“只看评分”和“预算／口味／价量解释”，不以单元测试替代产品验证。
3. **接入真实报价与购买后反馈。** 外部价格作为带时间的参考；用户实际选择与品饮结果用于验证预测，经过独立样本和人工复核再更新全局方法。

## 可验收的行为

- 预算是硬约束。单位价更低但总价超预算，仍不能成为本轮首选；所有候选超预算时明确不推荐。
- 用户明确按单位价比较、愿意接受两种容量，且其余条件相同时：¥50/500ml 的单位花费优于 ¥60/300ml，不能因输入顺序反过来。
- 用户只想喝 300ml 时，大杯的低单位价不自动压过合适容量。
- 价格、容量、币种或包装不明时，暴露缺失项，不计算伪单位价；不混合堂饮与外带作市场结论。
- 评分缺失时仍能说明价格差，但不能据此判断品质优劣；高分候选也不能绕过明确的风格或预算限制。
- 回答展示每个被推荐候选的实际杯价与容量，说明为什么选、备选多花多少，以及尚不确定什么。
- 同一任务在两个 API 和多轮追问中保持约束；改变预算、容量或风格后重新计算，不能继续沿用旧结论。

## 反馈怎样形成差异化

每次反馈应绑定**实际买的酒、实际价格与容量、当时的候选和推荐理由**。重点问题是：“这个价格还会再买吗？”“是口味不合适，还是这个价格不值得？”

这样可以分别改进：酒款／价格事实、个人口味、个人愿意支付的溢价，以及推荐方法。一次“太贵”不能直接降低公共酒款评分，也不能推断用户永远不愿为某个风格加价。

事实冲突交给数据复核；用户自己确认购买对象与感受；全局推荐方法的变更用固定案例、新案例和人工比较验收。最终积累的差异化资产是**带场景的报价与选择证据，以及经购买后反馈检验的决策经验**。这是建设方向，尚未证明收益。
