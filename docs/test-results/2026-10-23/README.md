# 全菜单上下文与取消机制验证 · 2026-10-23

本轮实现了知识追问的完整菜单上下文与多模态容器取消接口。整仓 `npm run check` 通过：961 项 Node 测试、38 项 Python 测试、类型检查和生产构建。

## 菜单上下文

每款酒都进入紧凑名册，包含酒名、酒厂、风格、ABV、菜单价格和容量。最多 8 款展开详细证据；点名后排、当前讨论的酒或同名歧义款时，按对应条目展开，保留来源标签和冲突说明。空或重复候选 ID 不合并不同条目。

新增 36 项合成测试覆盖 1/8/18/24/30/31/147 款菜单、后排引用、同名消歧、activeBeer、字段缺失、来源保留、注入文本和快照隔离。另用现有 [147 款 MBCB 目录](../../../data/events/mbcb-2026-red.json) 组装本地上下文，逐行核对全部身份与酒厂：

| 问题 | 名册条目 | 详细证据条目 | 上下文字符数 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 有什么酒，全部列出来 | 147 | 8 | 11844 | 全部条目保留 |
| #498 有什么特点 | 147 | 8 | 11908 | 保留全单并展开 #498 |
| #149 的来源呢 | 147 | 8 | 11915 | 保留全单并展开 #149 |

这些是本地上下文组装结果，没有调用业务模型。目录中的事件编号用于本表，不能套用为今日酒吧酒头编号；完整条目覆盖也不表示酒花、经典款依据或价格资料已经齐全。147 款上下文规模已测，更大菜单的提示词成本仍随条目数增长。

## 取消机制

新增 14 项离线测试覆盖已取消请求、命中缓存前取消、提供方执行途中取消、迟到成功与失败、备用提供方、同步报错、信号透传与错误脱敏。调用方取消后，不继续备用请求，不使用或缓存迟到结果。同步抛错仍按原有分类进入正常回退逻辑。

本轮只提供取消接口，尚未接入整个飞书链路的截止预算。不响应取消信号的底层操作可能继续运行，容器会丢弃其结果。

## 验收中的纠错

初稿有两个问题：全单名册另加了 30 行上限；取消重构使同步抛错绕过错误分类和回退。主代理复现后，各交给 Coding Plan 一次定向质量修正，复用原有合格改动。

旧测试还要求整个上下文不得出现第 147 款，与完整名册目标直接冲突。交接把它设为只读，导致 B 修正任务如实返回 blocked。主代理保留该原始回执，只在采用副本中把断言改为“名册含全部 147 款、详情只展开 8 款”，随后重跑全部检查通过。没有为凑绿灯给酒名设特殊分支，也没有追加重试或切换模型。
