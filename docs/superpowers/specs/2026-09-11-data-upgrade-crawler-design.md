## 方案比较
1. 推荐：增量合并 + SQLite 持久队列。复用现有 Python SQLite 与 Playwright，能备份、回滚、断点恢复，维护成本较低。
2. 直接换库：快，但会丢旧库独有数据及 legacy_dup/索引等本地修复，拒绝采用。
3. 直接全量扩爬：覆盖可能更广，但当前价格关联和字段污染未解决，成本高，延后。

## 第一阶段：导入与质量门禁
新增独立 import/audit 命令，提供只读 --dry-run 和显式 --apply。源库只读，目标库先用 SQLite backup 备份；记录源 SHA-256、表结构、行数和变更计数。
先在暂存库合并，再执行完整性与查询回归，事务提交。目标既有表、索引、legacy_dup 和旧库独有行保留。禁止照搬覆盖源 schema。
使用 provider + source ID 作为稳定键；同名不同酒厂不合并。非空不被空覆盖；冲突保留来源与时间证据，无法判新旧的进入复核清单。时间统一转换到 UTC，保留原值，处理秒/毫秒/字符串。
门店价格独立存 observation：保留来源 URL、门店、币种、容器、容量、价格、采集时间及原始值。重复导入不增行；报价变化保留历史。
零价/缺容量/未知币种/异常包装标记不可比较，不参与性价比；停产提示迁为 discontinued，style 标为待补，原始值留审计记录，不猜测真实风格。

## 第二阶段：自动缺口队列
在本地 SQLite 维护 crawl_jobs：source、实体 ID/URL、缺字段、原因、优先级、状态、尝试次数、next_attempt_at、最后错误、租约到期时间。
优先级：用户查询未命中且可定位的实体 → 价格表尚未关联的酒款 → 用户实际会用到的缺字段 → 停产风格修复 → 过期门店报价 → 新地区探索。
未命中和数据库故障必须区分；无可靠实体 ID/URL 时进入实体解析/复核，不猜 URL 或将故障当作待补酒名。
任务去重键为来源 + 目标 + 任务类型，重复审计不反复新增。状态 pending/running/succeeded/retry/blocked/review；进程异常后按租约恢复。每轮限定条数、并发和最长时长，有锁防重复启动。

## 第三阶段：实际补采与回写
任务 worker 复用当前浏览器 driver，增加明确目标列表输入以及门店解析器；新包脚本在可读取后只复用经检查的解析规则，移除旧机路径与临时会话依赖。
先小批只读抓取落原始结果，再校验实体、来源、字段和单位；成功后事务写入并重跑缺口审计，只有缺字段实际补齐才标 succeeded。
网络故障有限重试、指数退避并遵守 Retry-After；403/登录验证/挑战页面标 blocked，暂停该来源，不做无休止重试。解析为空标 parser_error，不表示网站没有酒或没有价格。
先跑一轮最多 20 个目标、并发 1；验证后配置每天一次有界补采。任务运行报告统计新增、补齐、冲突、失败、剩余缺口；无变化保持安静，仅有效变化、失败或需用户处理时通知。定时由 Codex 支持的自动化创建，不手写系统 cron。

## 第四阶段：项目消费
保留菜单现场价为当前决策依据。venue_prices 作为带来源和时间的外部参考，仅同币种、同消费形式、容量可比较时使用；不使用即时汇率，不把海外价格转换成中国现价。
lookup 层提供可追溯价格证据，并区分未收录/已收录无评分/数据源故障。随后让统一 runBeerDecision 入口消费这些证据，避免两个 API 各维护一套数据逻辑。

## 验收
- 对真实源库出只读审计；导入前后源文件 hash 不变。
- 临时数据库验证首次导入、重复导入零新增、冲突保护、事务失败回滚、旧数据和索引保留。
- 容量与价格 fixture 覆盖 pack、oz/ml、小数逗号、零价、多币种以及未知规格。
- 缺口队列覆盖去重、优先级、超时租约恢复、重试上限、来源阻塞、并发锁；禁止空结果假成功。
- 抓取 fixture 覆盖目标详情与门店页面；实际小批抓取失败时如实报告，不用 fixture 通过代替联网成功。
- 查库实际命中、价格证据展示、已有 npm test/typecheck/build 全通过；数据库和用户原始数据保持 Git ignored，GitHub 只提交代码、匿名测试 fixture 和文档。
