## 飞书服务侧计时

真实 handler 在入队前记录接收时间，出队时记录开始时间，等待完整 `replyFeishuMessage` 返回后记录结束时间。整轮耗时包含排队；另报处理、回发及图片下载、agent、记忆写入耗时。每个入队消息各有独立记录，日志只含枚举和数值，不记录聊天身份、消息正文、图片或提供方错误。

新增 17 项测试使用真实 handler、真实队列和计时模块；agent、飞书 API 与存储依赖为合成替身，不访问实际服务。

| 场景 | 检查内容 |
| --- | --- |
| 同聊天连续两条 | 后一条等待前一条，等待计入整轮耗时 |
| 不同聊天 | 相互独立，计时不串轮次 |
| 完整回复尚未完成 | 不提前落完成记录 |
| reset、目录、标记与重投 | 保持原有路由、回复和去重行为 |
| 下载或模型抛错 | 保留原错误提示及会话失败状态；计时为 `processing_error` |
| 技术警告 | 保留处理失败，不因为提示已送达就记成功 |
| 正常但资料稀疏 | 可解释缺口的正常回答仍为 `ok` |
| 回发失败 | 记录 `reply_error`，区别是否发出兜底消息 |
| 计时日志写失败 | 消息处理继续完成 |

独立的四场景探针额外验证模型抛错、下载抛错、技术警告和正常稀疏回答。初稿曾把模型错误提示记为成功，主代理复现后交给 Coding Plan 一次定向修正；源码和错误测试预期一起纠正，未以修改测试来迁就误判。

## 结果边界

计时结束点是服务侧回发成功的代理指标，尚未证明飞书客户端已经显示。`replySucceeded=true` 只代表消息送达接口成功；错误提示可能已送达，但 `result` 仍为错误，不能算一分钟体验成功。`ok` 也不单独证明酒款事实、菜单完整性或推荐质量。

本轮没有真实图片 OCR、业务模型调用或飞书多轮，没有新增酒款资料、价格或数据库导入，未重启运行服务。截止预算尚未激活；还需首轮本地关键路径、知识档案/风格通识/SP、完整首轮逐款解释、真实来源价格和客户端可见时间验收。20 条试酒师金标仍是场景定义。
