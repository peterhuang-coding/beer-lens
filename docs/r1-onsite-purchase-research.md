# R1 现场购买决策助手调研

查阅日期：2026-09-15。调研对象是 Beer Lens 的首个产品方向：用户在酒吧、餐厅或瓶子店面对一张陌生酒单时，能否通过一次拍照或粘贴文本，在预算、容量、口味和酒精度约束下快速选出“这次最合适买哪款”。

## 结论

R1 值得继续，但 MVP 不能定义成“拍酒单查评分”。这条能力至少从 Picky Pint 的 2014—2015 年版本起就已存在，Hoppy 当前产品也明确把流程定义为拍菜单或冰柜、识别酒款、批量展示 Untappd 评分与 check-in。BeerCoach 和开发中的 Barley Lens 又把个性化口味推荐放进相同入口。仅靠 OCR、酒款识别、公共评分或个人口味画像，无法形成稳定差异。

Beer Lens 应把自己放在购买漏斗的**约束决策层**：识别完成后，把菜单中的酒款、杯价、容量、消费形式和证据转换成可复算的选择，回答“预算内选哪杯”“多花多少换来什么”“哪些候选因为信息缺失不能确认”“现在是否应该先不买”。

首版 MVP 建议保持为便携 Skill，不要求用户登录 Untappd，也不先建设社区、交易或完整个人档案。前台可以接受图片或文字，但验证应分两步：先用结构化文字酒单证明决策规则有效，再用真实图片验证整条现场链路。否则 OCR 错误会掩盖决策层是否真正有价值。

继续投入仍有一个未验证前提：真实用户是否愿意在点单前拍照，并认为预算、价量和取舍解释比直接看评分或问店员更省事。当前公开资料和仓库测试只能证明竞品形态存在、代码能力存在，不能证明用户需求或留存成立。

## 市场位置：不争“发现”，占住“下单前决定”

用户的现场路径可以拆成五步：看到酒单、识别候选、加入约束、比较取舍、作出选择。Untappd 的强项覆盖发现、搜索、评分、记录和附近菜单；Hoppy 把批量识别与 Untappd 评分组合起来；BeerCoach、Barley Lens 把口味画像和新鲜度作为推荐信号。Beer Lens 最有机会占住的是中间三步中的后两步——把真实报价和用户当次约束转成明确决定。

```text
看到酒单 → 识别酒款 → 加入预算/口味/容量约束 → 比较取舍 → 下单
             通用视觉/Hoppy          Beer Lens 核心层          交易/社区
```

这不是“更完整的啤酒数据库”定位。数据是输入资产，MVP 的直接价值是一个可解释、可复算、不会越过硬约束的决策结果。后续只有把实际购买、实付价格和“这个价还会不会再买”接回来，数据和反馈才可能形成长期壁垒。

## 外部证据说明了什么

1. **拍照识别不是壁垒。** Hoppy、Picky Pint 和 Barley Lens 覆盖了同一入口，BeerCoach 也已把扫描列入近期方向。
2. **公共评分有明确需求，但主要解决“大家觉得怎么样”。** Untappd 的应用商店元数据与近期评论显示，用户大量使用它记录、回看并在购买前参考评价；这与“在具体预算和规格中怎么选”不是同一个问题。
3. **识别完整性是直接竞品的真实风险点。** Hoppy 2026-02-15 的一条近期评论称，11 款 tap list 只返回 3 个结果，其中 2 个错误。样本只有一条，不能推断整体准确率，但足以把“完整提取 + 错误可见”列为 MVP 的硬验收，而不是只展示成功匹配项。
4. **个性化和新鲜度会快速成为行业标准能力。** BeerCoach 已提供个人匹配分，Barley Lens 计划同时使用口味画像、实时 tap 数据和新鲜度。因此 Beer Lens 不应把“了解你的口味”单独当作长期定位。
5. **中文可能是切口，但尚不是已证明优势。** Hoppy 的 iOS 元数据只列英文；Picky Pint 只列英文和西班牙文；BeerCoach 元数据列出中文。语言列表不等于中文酒单识别质量，Beer Lens 仍需在中文、双语、音译和酒厂别名样本上实测。

## MVP 产品合同

一次调用只承诺完成一个决定：在用户给出的当前菜单和当次约束中，返回最多三个有用选择，并让用户能检查结果为何成立。

### 输入

- 一张菜单、tap list、冰柜标签或一段粘贴文本；
- 用户当次约束：预算、期望容量、风格、苦度、ABV、是否想尝新；
- 可选公共证据：同一酒款和酒厂的评分、评分数、来源链接与观察时间。

### 输出

- 首选：名称、菜单编号、实际价格、容量和单位价；
- 备选：相对首选多花或少花多少，换来什么差异；
- 可选探索项：仅在确有不同价值时出现；
- 排除与不确定项：超预算、规格不明、字段未知、身份未核实；
- 明确范围：只能说“这张菜单中”，不能说“市场最划算”。

### 明确不做

- 不把 Untappd 登录、社区、check-in 或交易支付放进首版；
- 不构造“评分 ÷ 价格”的万能分数；
- 不在堂饮、外带、整组、不同币种或不同包装之间做伪比较；
- 不因识别到几款就假装整张菜单提取完整；
- 不在用户未确认购买对象时写入长期偏好。

## 当前便携 Skill：已经具备什么

仓库中的 `skills/beer-lens/` 已经覆盖了首版决策内核：

- 中英文触发说明，用户无需登录 Untappd；
- 菜单字段契约，未知事实保持 `null`；
- 预算、ABV、IBU、排除风格等硬约束；
- 总价和每 100ml 单位价计算；
- 单位价不能绕过总预算；
- 首选、备选和差价输出；
- 评分身份、证据和隐私边界；
- 脚本无第三方运行依赖，可从仓库外目录调用。

这使 Beer Lens 已经不只是 prompt，而是“领域说明 + 确定性决策 helper”的便携 harness。

## 开发前必须补的缺口

### P0：决定是否可信

1. **Offer 规格模型。** 在每个报价上增加 `currency`、`servingMode`（堂饮/外带/零售）、`packageType`、`quantity`、`bundle` 和原始规格文本。只有同币种、同消费形式且规格可换算时才比较单位价。
2. **字段级证据与置信度。** 价格、容量、ABV、IBU、酒名和酒厂分别携带来源、原文和置信度。低置信字段不能静默进入硬约束计算。
3. **完整性确认。** 输出已识别行数、疑似遗漏行和需要确认的行。Hoppy 的近期单条负评说明“只返回少量看似成功结果”会直接破坏信任。
4. **取消未经验证的综合排序魔法。** 当前 `balanced` 模式中的评分、偏好和单位价权重是工程启发式，不是外部数据证明。MVP 应优先采用硬过滤后分维度解释，只有通过任务集和用户比较后再固化权重。
5. **结构化决策结果。** 除自然语言外，返回 `eligible`、`excluded`、`needsConfirmation`、`comparisonBasis` 和 `decisionReasons`，供不同宿主稳定渲染。
6. **可观测性。** 每轮记录图片处理、字段提取、身份匹配、决策脚本和回复生成的延迟、失败原因、模型和估算费用；默认不保存原始图片。

### P1：形成连续体验

- 把“当前菜单快照”从 Skill 指令升级为明确的宿主状态接口，支持“第 2 款”“预算改到 80”“只喝 300ml”的重新计算；
- 打包最小中英文别名与常见风格词典，避免便携版完全依赖宿主知识；
- 增加用户确认后的购买反馈事件，但仍把“喜欢味道”和“这个价格会不会再买”分开；
- 等价格与规格链路稳定后，再评估新鲜度、同款跨店报价和社区数据贡献。

## 现有 helper 快跑结果

2026-09-15 使用当前 `skills/beer-lens/scripts/decide-menu.mjs` 对 10 个任务做了无模型调用的基线快跑。结果用于定位实现缺口，不代表完整 Skill、图片识别或用户体验成绩。

| 任务 | 当前结果 | 判断 |
| :--- | :--- | :--- |
| R1-01 预算优先于单位价 | 推荐 A，排除超预算 B | 符合核心期望 |
| R1-02 期望容量优先 | 仍把 500ml 大杯排在 300ml 前 | 不符合；缺少目标容量约束 |
| R1-03 未知价格 | 已将未知价格候选排除为不确认 | 符合核心期望 |
| R1-04 未知容量 | 已阻止未知容量候选参与单位价选择 | 符合核心期望 |
| R1-05 堂饮与外带 | 直接把四罐装按单位价排到堂饮杯前 | 不符合；缺少消费形式可比性 |
| R1-06 同酒多杯型 | 两个报价都保留，但输出只有相同菜单编号，不能稳定指向具体 Offer | 部分符合；需要独立 `offerId` |
| R1-07 全部超预算 | 返回无推荐 | 符合核心期望；还需补“最低放宽到多少” |
| R1-08 IBU 未知 | 未把未知 IBU 候选当作确认合规 | 符合核心期望 |
| R1-09 不同币种 | 直接按数值把 8 美元排在 50 元前 | 不符合；当前只有顶层币种，不能表达混合币种 |
| R1-10 连续追问 | 未直接运行 | 依赖宿主保存菜单快照和约束替换，不属于纯 helper 单次输入 |

因此第一项代码工作不应是增加更多评分源，而应先升级 Offer schema、比较资格和结构化输出。否则识别越多，错误比较的覆盖面也越大。

## 最小体验与验证方案

### 体验流程

1. 用户拍一张酒单，或粘贴 3—15 行文字；
2. 系统先展示识别摘要：“读到 12 行，2 行价格不确定”，允许一键确认或修正；
3. 用户输入一句约束，例如“70 元以内、不太苦、第一杯”；
4. 系统返回首选、备选、价量差、满足的约束和未知项；
5. 用户可改预算、问菜单编号或选择“先不买”；
6. 仅在用户确认购买后，询问是否记录“这个价格还会不会再买”。

### 对照实验

使用同一批真实菜单和相同任务，比较三种路径：

- A：用户手工使用 Untappd 或搜索逐款查询；
- B：把图片直接交给通用多模态助手；
- C：Beer Lens Skill。

首轮建议 5—8 名精酿消费者、每人 3—4 个任务，至少形成 20 个有效决定。此规模只能发现明显可用性和规则问题，不能证明市场需求。

### 指标

| 层级 | 指标 | 首轮门槛建议 |
| :--- | :--- | :--- |
| 提取 | 酒款行召回、价格/容量字段正确率、行关联错误 | 不允许静默漏行；关键字段错误必须可见并可修正 |
| 决策 | 硬约束违规率、价量算术正确率、人工首选一致率 | 硬约束违规 0；算术 100%；10 个任务至少 9 个符合人工期望 |
| 体验 | 完成一次选择的时间、需要人工修正次数、选择信心 | C 相比 A/B 至少减少一个明显步骤；是否更快由实测决定 |
| 运行 | 端到端 p50/p95、各阶段耗时、请求失败率 | 先测基线；若常态需要等待一分钟，不能称为现场 MVP |
| 成本 | 每次图片调用、文本调用、外部查询和重试的实际费用 | 记录 p50/p95 与失败重试成本；费用上限由部署模型和使用频次决定 |
| 结果 | 是否购买、是否喝完、这个价格是否愿意再买 | 只作为后续闭环，不用单次点赞自动改全局规则 |

当前仓库已有延迟记录能力，但历史监控样本只覆盖少量请求；图片能力的模型超时上限达到 180 秒，代码注释中的历史观察约为 68—76 秒。这些数据不是当前版本基准，却说明正式试点前必须实测端到端延迟。确定性 helper 应单独计时，以区分“决策逻辑慢”还是“视觉/模型链路慢”。

## 下一步建议

1. **先补 P0 Offer schema 和结构化决策输出。** 这直接决定是否会做出伪比较。
2. **把 10 个任务做成可重复评测。** 先测纯文本/结构化输入，再加入 5 张新的真实中英文酒单；旧图片不能继续重复充当市场验证。
3. **做一次三路径人工对照。** 核心问题不是 Beer Lens 能否回答，而是相对 Untappd、通用助手和店员建议是否更快、更可信、更容易做决定。
4. **暂不做社区和数据商业化。** 在单次决策价值未证明前，社区只会扩大范围，不能补足核心体验。
5. **下一次产品决策只选一件事。** 建议确认“首批用户锁定酒吧现场消费者”，并将首个可交互入口定为“拍酒单后先确认结构化报价，再给决策”；工程验收先从文字任务开始。

## 未知项与反例

- 没有真实用户访谈或现场观察，无法确认拍照动作的接受度；
- 没有对 Hoppy、BeerCoach 或 Barley Lens 做同图、同任务实测，不能宣称 Beer Lens 已领先；
- Hoppy 和 Picky Pint 的应用商店评价样本很小，只能作为个案信号；
- 语言列表不能证明中文 OCR 和中文实体匹配质量；
- 店员建议可能在库存、新鲜度和现场状态上显著优于任何离线 Skill；
- 如果菜单不展示价格或容量，Beer Lens 的价量差异会明显收缩，此时它更接近普通口味推荐；
- 如果用户只认大众评分且不关心预算、规格和解释，Hoppy 或 Untappd 已经足够。
