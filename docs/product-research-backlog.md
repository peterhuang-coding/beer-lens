# 产品方向调研与白班决策

更新：2026-09-14。状态：待选择，以下均为待验证假设，不是已完成的市场调研或产品承诺。

[Notion 决策与调研入口](https://app.notion.com/p/3db3285284df81e397d1e520c2f7fece)（需对应工作区访问权限）

## 共同目标

帮助用户判断“买什么最合适”，同时积累两类资产：我们自主整合并持续维护的领域数据，以及经真实购买、品饮反馈检验的决策方法。数据保留来源、时间、规格和使用边界。

[购买决策设计](purchase-decision.md) · [当前测试边界](testing.md) · [执行主线](../.claude/autopilot/mainline.md)

## 五个调研待办

所有方向当前均为「待白班选择」。优先级是建议，不代表已批准执行。

### R1 · 现场购买决策助手（建议先做）

- [ ] 验证用户是否愿意在点单前拍酒单，比较杯价、容量、预算与口味，而不只查询酒名。
- 调研：对比至少 3 个真实替代方案（评分应用、通用多模态助手、店员建议等）；记录来源与日期，未知项明确标注。整理 10 个购买任务，覆盖预算不足、容量取舍、未知价格、不同消费形式。
- 交付：一页对比、带人工期望的 10 个案例、一个最小体验方案和成本/延迟测量方案。
- 白班决策：首批用户是否锁定酒吧现场消费者？先做拍酒单还是文字点单？
- 继续投入条件：能说明相比现有替代方案多解决哪项真实决策；最小验收涵盖预算硬约束、价量算术、首选/备选差价与证据缺失。
- 限制：当前性价比决策尚未完整实现；历史图片样本少，不能宣称产品准确率。

### R2 · 个人品饮与回购助手

- [ ] 验证“这个价格还会再买吗”能否比普通打分更好地改进下次选择。
- 调研：比较至少 3 种反馈交互；设计 10 个案例，涵盖否定表达、另一款、菜单编号、改口和删除记忆。
- 交付：最小反馈字段与交互草案、对象绑定验收集、个人记忆修改/删除规则。
- 白班决策：先解决单次买后反馈，还是长期个人偏好？用户愿意记录多少字段？
- 继续投入条件：能绑定实际买的酒、实付价、容量和推荐上下文；事实、口味、愿付溢价分开处理，无法确认对象时先澄清。
- 限制：现有否定偏好、反馈对象归因和禁写等缺陷需先修；用户样本需由用户提供或另行安排，代理不能虚构访谈。

### R3 · 酒吧/瓶子店经营助手

- [ ] 验证商家是否需要菜单数字化、价格维护、店员推荐和顾客偏好总结。
- 调研：比较至少 3 个商家现有工作流或工具；列出菜单更新、缺货、杯型、推荐利益冲突的成本与风险。
- 交付：一个门店试点方案、导入样表、访谈提纲，以及节省维护时间的测量方法。
- 白班决策：是否能找到试点商家？由商家付费还是作为消费者产品的数据合作入口？
- 继续投入条件：有真实试点意愿、明确的数据维护责任和可验证的节省时间目标。
- 限制：库存和在售价格不能靠旧图片推断；本轮不联系商家、不承诺交易或合作。

### R4 · 精酿数据与报价服务

- [ ] 验证自主整合的数据是否可以独立服务搜索、推荐、价格比较或行业应用。
- 调研：梳理买方场景、至少 3 类替代数据服务、来源使用条件、更新成本；对新资产包形成覆盖与缺口清单。
- 交付：数据字典、来源/时间/规格矩阵、质量报告、缺口队列与有界补采方案、服务成本估算。
- 白班决策：先服务 Beer Lens 内部，还是验证外部 API/数据订阅需求？
- 继续投入条件：有具体消费者与字段需求，可解释实体去重、更新时效、可用范围及单位维护成本。
- 限制：多表记录不能相加宣称独立酒款；未核实的来源使用权限和价格可比性必须保留为待核验项。

### R5 · 从反馈改进 Skill 的多模态评测平台

- [ ] 验证从 Beer Lens 提炼的“失败案例 → 人工复核 → 规则候选 → 对照评测 → 发布/回滚”能否复用。
- 调研：对比至少 3 个评测/观测/反馈工具的一手资料；区分知识检索、运行轨迹、任务成功和真实用户结果。
- 交付：流程图、带版本的 case 格式、人工审阅界面草案、固定集与留出集策略、发布与回滚标准。
- 白班决策：先作为 Beer Lens 内部工具，还是单独开发者产品？人工复核由谁负责、每周能投入多少时间？
- 继续投入条件：先用 Beer Lens 的真实失败案例证明一轮改进且无关键回归，再谈跨领域复用。
- 限制：单次点赞不自动修改全局 Skill；错误标签不是正确答案；测试 HTTP 成功不等于任务成功。

## 每项调研的统一交付

调研由代理负责资料整理与可复现分析，方向由用户拍板。每份报告必须包含问题、带访问日期的一手来源、事实/推断/未知项、替代方案、差异化假设、验证成本、反例和建议。无法获得的访谈或数据标为阻塞，不伪造。

白班只需做一个选择：继续、缩小范围或放弃；选择继续时，同时确定一项最小执行任务和验收标准。建议先 R1，R2 作为后续体验闭环；R3–R5 保留为候选，不同时开发五条线。

## 白天定方向，晚上执行

1. 白班在 Notion 写决策：方向 ID、研究或开发、唯一任务、验收标准、允许改动范围、时间/费用上限。代理将明确决策同步到 Git 主线并保留来源链接；冲突时暂停澄清，不把勾选待办当作开发授权。
2. Git 中的主线记录已确认的执行状态；Notion 是讨论与决策入口。当前为手动同步，没有实现双向自动同步。
3. 夜班启动前读取主线、最近摘要、Git 状态和远端更新。仅执行已批准任务；未选定任务、缺少必要预算或出现范围冲突时停在待决策状态。
4. 每轮最小改动、实际验证、独立提交、写交接。工作区已有改动需保护；不能把数据库、私有记忆和原始用户记录混入提交。
5. 验收达成、时间/费用上限、连续 3 轮无增量或需要产品决策时结束。待批准的方案不自动变成下一项任务。
6. 次日交付：commit/PR 链接、真实测试结果、失败案例、未完成项，最多 5 个待决策问题。事实或数据修正与全局方法变更分别验收；全局方法需人工比较与回滚点。

当前没有排定自动执行时间，也没有启动夜班。待确认北京时间的启动/停止时间后，使用 Codex 任务自动化承载定时执行；主线里“待选择”时不得自行开工。自动化运行还依赖电脑及本地执行环境可用。
